# التثبيت

يغطي هذا الملف العمل مع مستودع الترسانة نفسه: نسخَه وإثبات سلامته. أمّا
تجهيز مشروع هدف فهو عمل Vanguard وهو موصوف في
[04-VANGUARD.md](04-VANGUARD.md).

## المتطلبات

| المتطلَّب | الأدنى | ملاحظات |
|---|---|---|
| `git` | أي إصدار حديث | أشجار العمل لازمة للعمل المتوازي (انظر [11-WORKTREES.md](../11-WORKTREES.md)) |
| Node | الإصدار 20 أو أحدث | يثبّت CI الإصدار Node 25؛ والأدوات ESM بلا تبعيات ولا تحتاج خطوة تثبيت |
| `gh` | موثَّق الدخول | لازم لمسار الإصدار فقط (انظر [14-CI-RELEASE.md](../14-CI-RELEASE.md)) |

ولا شيء آخر عن قصد: لا Python، ولا تثبيت حزم، ولا حزمة تجميع. فإذا بدت
خطوة أدناه محتاجة لتبعية، فذلك علّة في الخطوة لا فجوة في الجهاز.

## انسخ وأثبت السلامة

انسخ المستودع، ثم شغّل بوابتَي القراءة فقط. تخرج كلتاهما بالرمز 0 على
شجرة سليمة، وكلتاهما آمنتان قبل تغيير أي شيء:

```bash
node scripts/verify-registry.mjs
node scripts/generate-catalog-json.mjs --check
```

تثبت الأولى أن السجلّ متّسق داخليًا (سبعة فحوص، موثّقة في
[08-VERIFICATION.md](08-VERIFICATION.md)). وتثبت الثانية أن النسخة الآلية
المُولَّدة مطابقة للمصادر، فـ `registry/catalog.json` وكل ملف `_index.md`
لكل نوع محدَّثة. فإذا فشلت إحداهما، أصلح الشجرة قبل بدء العمل؛ فالبوابة
الحمراء وقت النسخ تعني أن الفرع وسط ترحيل، لا أن البوابات استشارية.

وتُفحَص سكربتات الصدفة بالطريقة نفسها التي يفحصها بها CI:

```bash
shellcheck scripts/*.sh .githooks/*
```

## ما هي `registry/catalog.json`

`registry/catalog.json` هي النسخة الآلية للفهرس. وهي مولَّدة من
`registry/VANTRILEX_CATALOG.md` مع الملفات الجانبية الستة عشر بصيغة JSONL
تحت `registry/data/`، ولا تُعدَّل يدويًا أبدًا (انظر
[07-CATALOG-GENERATION.md](../07-CATALOG-GENERATION.md)). يقرأها Vanguard
بصيغة JSON وقت الانتقاء؛ ويقرأ البشر صيغة Markdown. والمخطط الذي يجب أن
يفي به الجانبان هو `registry/schema/catalog-v3.schema.json`، وهو موثّق في
[06-REGISTRY-SCHEMA.md](../06-REGISTRY-SCHEMA.md).

## كيف يستهلك مشروع هدف الإضافة

لا ينسخ مشروع هدف هذا المستودع لأجل محتوياته. بل يستقبل السطح المُسلَّم
تحت `.opencode/`: نقطة دخول الإضافة، ووكلاء الأدوار، وأوامر المشغّل،
والمهارات المنقولة. ووقت التشغيل، يكتشف Vanguard حالة المشروع، وينتقِ
لبّ Tier-0 مع مكوّنات Tier-1 التي تتطلبها الحزمة، ويثبّتها بأوامر حقيقية،
ويثبّت إصداراتها في قفل طقم المشروع، ويتحقّق من تحميل كل واحد منها. ونقاط
دخول المشغّل هي ملفات الأوامر الأربعة:

| ملف الأمر | قصد المشغّل |
|---|---|
| `.opencode/command/equip.md` | اكتشاف حالة المشروع وتجهيز الطقم |
| `.opencode/command/doctor.md` | تشغيل فحص النظام قبل الإقلاع |
| `.opencode/command/prime.md` | إخراج `CONTEXT ANCHOR` للجلسة عند بدئها |
| `.opencode/command/release.md` | تشغيل مسار الإصدار |

تُسلَّم Prime وVanguard وDoctrine ملفاتِ مهارات تحت `.opencode/skills/`؛
وتلحق بهم Workflow-Forge وقت التجهيز، حين يثبّتها Vanguard في مسار الخطوة
4 ويبرهن على التثبيت بإعادة القراءة. وتعمل بالترتيب Prime ثم Vanguard ثم
Workflow-Forge ثم Doctrine: توجيه مرة واحدة لكل جهاز، وتجهيز مرة واحدة لكل
مشروع هدف، وتصميم سير العمل عند بدء كل مهمة، ثم العمل. وعقودها
[01-OVERVIEW.md](01-OVERVIEW.md) و[04-VANGUARD.md](04-VANGUARD.md)
و[05-DOCTRINE.md](05-DOCTRINE.md)، مع عقد Prime الخاص الذي يحمله
`.opencode/skills/vantrilex-prime/SKILL.md`. وأمر `prime` أعلاه لا علاقة له
بمهارة Prime: بل هو مُهيّئ سياق الجلسة.
