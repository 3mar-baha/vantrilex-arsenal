## Batch order (deterministic across sessions)

Batch order is the **raw output order of `git ls-files registry/skills/`**
(bytewise path order; verified identical to `git ls-tree -r HEAD --name-only`
on this clone, 0 order differences, 1,460 == 1,460). It is never re-sorted
with a culture-aware sort; any session that re-derives the list from
`git ls-files` gets the same sequence.

## Batch numbering convention

`t2-bNNN`, `NNN` zero-padded to three digits, `t2-b001` … `t2-b146`.
10 consecutive files per batch in the raw `git ls-files` order; batch `t2-b001`
takes lines 1–10, `t2-b002` lines 11–20, and so on. `1,460 / 10 = 146` exact;
no partial tail batch. One batch = one commit.

## Tier-2 acceptance standard — `t2-v1`

`standard_version: "t2-v1"` is the stamp used on every tier-2 ledger row this
lane appends. Meaning, in full: **tier-2 v1 is the mechanical card standard
below — six rules applied to the flat `registry/skills/<id>.md` catalog cards.
It is NOT `w26-v1`; the `w26-v1` standard (the seven SKILL.md body headings,
frontmatter `[name, description, source]`) does not apply to these files and
is never required of them.** No upstream prose is rewritten, paraphrased or
"completed" under `t2-v1`.

The six rules (mechanical only):

1. **File hygiene** — strict UTF-8, LF line endings only (no CR/CRLF),
   exactly one trailing newline, no trailing whitespace or tabs on any line
   (same hygiene class as `verify-skills.mjs` check 8).
2. **No placeholder tokens** — no `TODO`, `FIXME`, or `coming soon`
   (word-boundary, case-insensitive, same regex class as the existing scans).
3. **No absolute paths** — no drive-letter paths (`C:\…`, `D:/…`) and no
   `/home/<segment>` paths (same calibrated drive-letter/`/home/` patterns as
   the existing scans).
4. **Duplicate verbatim `**Description:**` lines** across the scanned set —
   reported as pairs; upstream descriptions are NEVER edited. Byte-identical
   descriptions that are upstream truth for distinct rows are left in place
   and recorded. Only mechanical, byte-identical boilerplate would be
   deduplicated, and only when the catalog treats the rows as one — this lane
   does no such dedup unless a pair is proven byte-identical AND
   catalog-identical, which is reported, not silently merged.
5. **Non-empty body** — the card must carry non-empty content (it is never
   empty, whitespace-only, or frontmatter-only).
6. **Raw URL scheme** — when a `**Raw URL:**` line is present, its scheme must
   be `https://`.

Enforcement: `node scripts/polish-scan.mjs --registry <files…>` (added by
F-08 as its own commit, `feat(polish): add --registry card scan mode`). The
default (no-argument) behaviour — the 47 `.opencode/skills` folders — is
byte-identical before and after the extension. The new mode prints defects
per file and exits 0/1/2 exactly as today.

## Ledger rows (F-08/F-10)

`registry/polish-ledger.jsonl` — one JSON line per file, appended (never
rewritten). Fields match the existing 46 rows exactly:

```json
{"id":"<path-or-folder id>","polished_at":"2026-11-12","polished_by":"vantrilex-implementer/tier2/final-fix","standard_version":"t2-v1","verify_skills_exit":0,"sha256":"<sha256 of the file at stamp time>","tier":2}
```

- `verify_skills_exit` is the measured `node scripts/verify-skills.mjs` exit
  code **at stamp time**; it stays `0` only if verify-skills exits 0.
- `sha256` is the sha256 of the file at stamp time (after any mechanical fix
  in that batch).
- `polished_by` is the literal string `vantrilex-implementer/tier2/final-fix`.
- `standard_version` is `t2-v1` (defined above).
- `tier` is `2` for every row this loop appends.
- `id` for a card is the card's id — the filename stem of the card
  (e.g. `a-share-skill`), and `_index` for `registry/skills/_index.md` —
  one row per file, 1,460 rows total. Existing 46 rows are untouched.

Generated-artifact caveat (`registry/skills/_index.md`): it is a build
output (`scripts/generate-catalog-json.mjs`, banner line inside the file).
This lane reads it and ledgers its sha at stamp time; it is **never
hand-edited**. If a future regeneration changes its bytes, its tier-2 row
goes stale exactly like any other regenerated-file row — that is expected,
and the row's meaning ("polished as of `polished_at`") is unchanged. A defect
in `_index.md` found by the scan is NOT fixed by hand; it is reported to the
Guide and the generator owner.

## Dispositions ledger

Files this lane cannot fix on its own authority (e.g. a placeholder whose
removal would require inventing upstream prose, or a duplicate-description
pair requiring a catalog ruling) are recorded in
`docs/dev/tier-2-dispositions-2026-11-12.md` — one line per stopped file,
with the reason. A stopped file is left byte-identical, is marked there, and
the loop continues; the stop is not silently absorbed.

Duplicate-description pairs are recorded in the same dispositions ledger
(`## Duplicate **Description:** pairs` section), never edited in place.

## Batch loop gates (per batch)

Per `t2-bNNN`: run the `--registry` scan over the slice → fix mechanical
defects in-slice (whitespace/newline/placeholder-report only; a placeholder
needing prose invention = STOP that file, mark it in the dispositions ledger)
→ `node scripts/verify-skills.mjs` (exit 0) → `node scripts/run-battery.mjs`,
record its exit (known red: section (c) `verify-catalog.mjs` until the syzygy
selection is owner-ruled — a named red with cause is acceptable; no gate is
loosened, ever; an unrelated new red = the batch is fixed or reverted before
the next) → append the slice's 10 ledger rows → commit EXACTLY the batch's
paths + the ledger append. A zero-defect batch commits only the ledger
append (the established tier-1 pattern).

## STOP rules

The loop stops and reports (no invention, no squeeze) when either:

- a slice shows **>25% defective files** (more than 2 of 10), or
- any placeholder would need **prose invention** to remove.

On STOP: the full list of affected files and the evidence, then wait for the
owner/Guide ruling.
