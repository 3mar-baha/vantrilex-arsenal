# 03 — Catalog Generation

`scripts/generate-catalog-json.mjs` turns the catalog Markdown plus the JSONL
sidecars into the machine-readable mirror and the per-kind indexes. It is the
only writer of those outputs. Nothing generated here is edited by hand.

## The pipeline

One run does six things, in order:

1. Read `registry/VANTRILEX_CATALOG.md` as bytes and detect malformed UTF-8.
   A malformed sequence is logged as a warning and decoded lossily; the
   registry verifier is what fails on it.
2. Parse the Markdown into records, one per table row, grouped into sections by
   their `##` heading.
3. Enrich each record from its kind's sidecar under `registry/data/`.
4. Validate every enriched record against the catalog schema.
5. Assert each section heading's declared row and default-selected counts match
   what was actually parsed.
6. Build the catalog object and write, or compare, the targets.

Any failure raises a `RegistryError`, which `main()` reports and exits non-zero.

## The kind tables

The generator is the single place a kind is wired in. Four maps and one list
decide everything:

- `KINDS` — the order: `skill`, `mcp`, `plugin`, `hook`, `agent`, `formatting`,
  `lsp`, `cli`, `theme`, `prompt`, `dataset`, `template`, `policy`, `benchmark`,
  `workflow`, `design.md`.
- `SECTION_KINDS` — the Markdown heading label to kind, such as `MCP Servers`
  to `mcp`.
- `SECTION_LABELS` — the reverse, kind to heading label.
- `INDEX_DIRS` — kind to its `registry/<dir>/` folder.
- `SIDECAR_FILES` — kind to its `registry/data/<kind>.jsonl` sidecar.

## The record shape

`RECORD_FIELDS` is the closed field set. A sidecar line carrying a key outside
it is rejected rather than ignored:

```text
id  name  kind  description  source  origin  install_cmd  version_pin
category  tags  when_to_use  phase  tier  verify_cmd  cost_note
verification  class  evidence  default_selected
```

`id` and `class` are required by the v4 schema, and `evidence` carries the
class's proof. A record without its class evidence fails validation and therefore
never reaches the mirror — the candidate files under `registry/candidates/` are
written by the migration and audit passes, not by this generator.

## Sidecar merge

`loadSidecar` reads one kind's JSONL file. Each non-blank line must be a JSON
object with a non-empty string `id`; an array, a scalar, or a malformed line
aborts the run naming the file and line. A `kind` field, when present, must
equal the file's kind, so a record cannot be misfiled.

`enrich` patches the base row by `id`. `id` and `kind` are never overwritten,
so a sidecar can refine a row but cannot re-identify it. A sidecar that is
absent is not an error: the base values are used and the absence is logged.

## Validation

Every generated record is validated against
`registry/schema/catalog-v4.schema.json` before anything is written. The run
aborts listing the first twenty violations. This is what makes the class-evidence
contract hold in the mirror as well as in the source.

## Targets

| Flag | Writes |
|---|---|
| none | `registry/catalog.json` |
| `--markdown` | also `registry/VANTRILEX_CATALOG.md` |
| `--indexes` | also `registry/<dir>/_index.md` per kind |
| `--stdout` | the JSON to stdout, and nothing else |
| `--check` | nothing; compares and fails on drift |

`--check` and `--stdout` are mutually exclusive, and an unknown or repeated flag
is an error. The formatting index is a hand-authored essay the records cannot
regenerate, so it is skipped and never overwritten; a kind with no records is
skipped too.

## Index shape

Each generated index carries a `Generated by ... Do not edit by hand` comment,
a count line, and one table per tier group in the order core, conditional,
extended, then untiered, with columns Name, Kind, Tier, When to use, Install.

## `--check` and repair

In check mode nothing is written. Each target is compared byte for byte; a
missing or differing file is collected, and the run then fails with the exact
regeneration command to run. That is why a drifted mirror is repaired by
regenerating rather than by editing.

## Reused by the verifier

`verify-registry.mjs` imports `loadCatalog`, `validateRecord`,
`findMalformedUtf8`, `byteOffsetToLine`, and `lineOf` from this module rather
than re-implementing them, so the verifier and the generator can never disagree
about what a valid record is.

Observed live 2026-10-22: `catalog_version` 4 with 2,837 records, and
`node scripts/generate-catalog-json.mjs --check` reporting every generated
surface `— ok`. The per-kind totals are in `06-REGISTRY.md`; a count quoted here
would go stale the next time a row lands.
