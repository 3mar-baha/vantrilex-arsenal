### 4.2 Fallback design: 3-minute agent-cron poll (specified, NOT built)

If hook scripts cannot reach Notion (push path dead), the relay still functions
on a bounded-staleness poll. This is a design specification for `p3-hooks` /
`p3-installpack` to implement — no code is written or run in this node.

- Components and responsibilities:
  - **Poller** (owner-side scheduled agent, 3-minute cadence): wakes, runs one
    bounded `query database` (filter `status == pending`, sorted oldest-first),
    hands rows to the Dispatcher, exits. Stateless; safe to overlap because of
    the claim rule below.
  - **Claim rule** (single-claimer invariant): a row is owned only after its
    `status` is successfully written `pending → acked`. Two overlapping pollers
    racing the same row resolve by last-write-wins on `acked`, but act-once is
    preserved because acting follows the ack write and re-reads state. Only one
    poller may be scheduled per consumer identity.
  - **Dispatcher**: routes by (`to`, `type`) to the owning consumer; pure
    routing, no payload interpretation beyond the routing columns.
  - **Ack Writer**: writes terminal state (`done` / `needs_omar` / `invalid`)
    after the consumer acts. `needs_omar` is the escalation sink, never a trash
    state.
- Interfaces (contracts, not code): tick → filtered query → per-row claim write
  → dispatch → terminal write. Every transition is a `pages.update` on routing
  columns only; `body` is read, never rewritten, by consumers.
- Trade-offs:

| Dimension | Hook push (preferred, if reachable) | 3-min cron poll (fallback) |
|-----------|-------------------------------------|----------------------------|
| Latency | Seconds | Bounded staleness ≤ 3 min + query skew; `expected_reply_by` ETAs must budget the skew (the 1.10 margin already absorbs it for ETAs ≥ ~30 min; short-ETA `alert` types should prefer push) |
| Cost | Event-driven, ~zero idle calls | ~480 queries/day idle per consumer; trivially within Notion rate limits but nonzero and forever |
| Reliability | Hook drop = silent loss unless reaped | Self-healing: any missed tick is caught by the next; but cron-miss-every-tick (machine asleep) stalls the queue with no alarm — needs a heartbeat row (`type == heartbeat`) whose age is itself the liveness signal |
| Correctness | Push ordering is transport ordering | Poll ordering is `created`/`expected_reply_by` sort — deterministic and auditable; races contained by the claim rule |
| Operability | Requires hook egress + secret on every producer | Requires exactly one scheduler per consumer + the owner-held config file (§5) |

- Alternatives considered and rejected:
  - 60s poll: rejected as the DEFAULT (4× the idle call volume for 3× latency
    gain that only matters to `alert` types; `p3-installpack` already owns a 60s
    loop spec — if it tightens the cadence it must justify it per message type,
    not globally).
  - Notion outbound webhooks: rejected — the Notion API offers no outbound
    webhook to arbitrary hook URLs, so push-from-Notion is IMPOSSIBLE on this
    API; push must originate producer-side.
  - Email/chat-bridge relay: rejected — unparseable payloads, no state machine,
    breaks the routing-only-columns contract.

# ADR-P3-02: 3-minute agent-cron poll as the reachability fallback ceiling

## Context
Hook push may be unreachable from hook-execution seats; the queue must still
function with bounded staleness.

## Decision
If push is dead, fall back to a stateless owner-side poller on a 3-minute
cadence with the single-claimer invariant (act only after pending→acked write),
