## 1. Portable manifest definition (V3 how-step 1, :4058)

The portable manifest names one component set with its constrained pins, in a single inspectable format:

- `manifest`: manifest format id, fixed `ld15-portable-v1`.
- `target`: install target, fixed `production` (the production target is the base; the legacy target is compatibility-only).
- `components[]`: each element carries `id`, `componentPin`, `modelPin`, `toolPin`, `install_cmd`, `verification`, `gate`.
- The three pins are constrained together: component pin, model pin, and connector-tool pin ship as one triple per element.
- `signature`: registry signature over the canonical pins (see §4).
- `signing`: custody note pointing at §6, never a key.

Sample element shape (all install paths null plus unverified per FBLD-15):

```json
{
  "id": "skill:ask-matt",
  "componentPin": "ask-matt@0.9.14",
  "modelPin": "free-tier@pinned",
  "toolPin": "connector-a@1.4.2",
  "install_cmd": null,
  "verification": "unverified",
  "gate": "MATCH"
}
```

## 2. Matching mechanism on the production target with gate parity (V3 how-step 2, :4059)

The same manifest installs on the production target, and gate results are compared against the originals:

- Install the identical manifest bytes on the production target — matching replaces rewriting, so no per-environment re-authoring is allowed to drift the set.
- Each element's gate result after install must equal its original gate result (`MATCH` equals `MATCH`).
- Parity is per element, never a summary claim without the table (see §7).
- Publishing rides the already-shipped release machinery; no new publishing system is invented for this slot.

## 3. Pin-mismatch rejects fail-closed, no silent swap (V3 how-step 3, :4060)

A package whose pins differ from the manifest is rejected, closed on failure:

- Mismatch decision is `REJECTED` with the diverging reason named (stale signature, absent pins, or gate divergence).
- A silent swap that changes the result while looking identical is forbidden: any pin change breaks the signature binding, so acceptance without re-verification is impossible.
- The probe proves this with a tampered tool pin that must reject (see `portable-match-probe.mjs`, `LD15-MISMATCH-REJECT`).

## 4. Signed registry publish with install-time verification and unknown-source rejection (V3 how-step 4, :4061)

- Publish to the registry is signed; install verifies the signature at install time against the canonical pins.
- A package with no signature is treated as unknown-source and rejected (`unknown-source`), never installed on trust.
- A package whose content no longer matches its signature is rejected (`signature-mismatch`), which is also the mechanism that enforces §3.

## 5. Generated-vs-authored kit-file boundary with generator plus inputs documented (V3 how-step 5, :4062)

The arsenal kit file — which carries every skill, agent, and hardware entry for the agent to choose from — is partly generated by this slot's mechanism and partly authored by hand. The boundary is drawn explicitly:

| Part | Origin | Generator + inputs |
|------|--------|--------------------|
| Manifest envelope (`manifest`, `target`, pin triples, `gate` table) | Generated | Generator: this slot's packaging mechanism; inputs: governed disclosure library + shipped release machinery |
| Pin values and gate results | Generated | Generator: packaging mechanism; inputs: component registry state at pack time |
| Custody notes, fallback line, open questions | Authored | Hand-written in this spec; never generated |
| Signatures | Generated at publish | Generator: registry signer; inputs: canonical pins (keys never in-package, see §6) |

No generated line is hand-edited after generation; a change goes through the generator or its inputs, then the manifest is regenerated and re-signed.

## 6. Signing keys under the control-level axiom, never shared, never in-package (V3 how-step 6, :4063)

Whoever holds the signing key owns the package identity — that is the control-level axiom, and key custody follows it:

- Signing keys are never shared between roles and never shipped inside the package itself.
- The manifest carries signatures and custody notes only, never key material.
- Who guards the keys, and how the axiom is applied to that guardianship, is open question Q1 (§9) — carried, never resolved here.

## 7. Per-element gate matching, never a blanket claim (V3 how-step 7, :4064)

Gate matching is measured element by element; a general announcement of matching without a reviewable detail table does not count:

```text
LD15-ELEMENT[skill:ask-matt]: pins PRESENT, gate MATCH
LD15-ELEMENT[agent:vantrilex-guide]: pins PRESENT, gate MATCH
LD15-ELEMENT[hardware:arsenal-kit-file]: pins PRESENT, gate MATCH
LD15-PER-ELEMENT-TABLE: RENDERED 3/3 MATCH
```

## 8. Hardening vehicle for the next slot (V3 how-step 8, :4065)

This packaging mechanism is documented as the vehicle that carries the next slot's hardening: hardening rides on matching, not on rewriting. Any later hardening assumes one set installed from one manifest with matching results, and extends that matching — it does not replace the set by re-authoring it.

## Exit criteria (V3:4095-4097, pass/fail rules)

- E1. The same component set installs from one manifest on the production target with matching gate results. Fail: any element gate diverges.
- E2. A pin mismatch is rejected fail-closed, without silent swap. Fail: a tampered package installs or a mismatch is absorbed silently.
